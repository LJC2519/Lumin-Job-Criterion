# LJC 分解模板（可独立使用）

> 把任意任务填进这个骨架。规则详情见 SKILL.md「第 1 步：模块化分解」。
> 来源：to-tickets 的 tracer-bullet + writing-plans 的 right-sizing + HTN 递归展开。
> 2026-10-26 升级：在 L0/L1/L2 之下新增 **L3 原子任务层（五要素）**——
> 拆到「任何人照着就能做完、不需再猜」为止。

```
L0 总任务：<一句话说清最终产出>

├─ L1 模块 A（能力域：程序/数据/材料/研究/协作/交付）
│   ├─ L2-A1 <小任务>｜产出：<可验收的东西>｜标准：<怎么算做完>｜依赖：无
│   │   ├─ L3-A1-1 <一句话动作>
│   │   │      输入：     <文件/数据/上文产物/权限——动手前必须具备>
│   │   │      输出：     <可点开/可运行/可验证的实体>
│   │   │      前置依赖： <必须先完成的 L3 编号；无则「无」>
│   │   │      执行顺序： <本父任务内第几步；可并行则标「可并行」>
│   │   │      完成标准： <可验证、不靠感觉；附验收命令/检查点更佳>
│   │   └─ L3-A1-2 …｜依赖：L3-A1-1
│   └─ L2-A2 …｜依赖：L2-A1
├─ L1 模块 B（能力域：…）
│   └─ L2-B1 …
└─ L1 模块 C（能力域：…）
    └─ L2-C1 …
```

## 填写纪律（不满足就继续拆或合并）

1. L2 四件套齐全（一句话 / 产出物 / 可验证标准 / 依赖），并继续拆到
   **L3 原子任务**——每个 L3 五要素齐全（输入 / 输出 / 前置依赖 / 执行顺序 / 完成标准）
2. L1 模块 3–5 个；L2 总数 ≤ 9；单个 L2 下的 L3 一般 1–5 个
3. **垂直切片**：每个 L2 切一条「窄而完整」的路径，独立可演示——不要按技术层横切
4. **右尺寸**：拆分点 = 验收者可能拒 A 而批 B 之处；准备工作并入需要它的任务
5. **先易后难**：让后续变简单的重构（prefactor）排最前
6. **宽重构例外**：机械全局变更按 expand–contract 走（加新→分批迁移→删旧）
7. **独立性标注**：无共享状态/顺序依赖的 L3 标「可并行」
8. **资源标注**：资源缺失的 L3 优先级自动靠前（先补资源再开工）
9. **拆不下去分两种**：⟲ 复合任务（执行期递归再拆）/ 黑箱（真缺口，如实标注）

## 分解完成后

1. **按 L3 检索，不按 L0 检索**：检索词从 L3 原子任务来（它最短、最具体）
2. **宽口径三分类推荐**（2026-10-26 升级）：不局限严格对口——
   · **直接使用**（高相关）：现成覆盖该 L3
   · **改造适配**（中相关）：底层能力对口，需改配置/换源/调参/拼接 → 必填改造要点
   · **思路参考**（低相关）：实现思路/工作流/检查清单可借鉴 → 必填「仅方法论借鉴」
   排序=相关度优先，同类内按 rerank 判分；宽口径 ≠ 硬凑，思路参考不得冒充成品
3. 标「可并行」的独立任务 ≥2 个 → 考虑并行执行（dispatching-parallel-agents）
4. 代码类任务可选：to-spec 固化规格 → to-tickets 拆工单 → implement 实施
5. 零命中的环节如实标缺口——不硬凑
